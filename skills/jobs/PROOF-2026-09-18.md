## RSS fetch-error guard (local-mode only, 2026-09-18)

The `mapping` right after the `http` processor in `rss-feed-engine` stops
the job with the fetch error before XML parsing. It was run on a
local-mode node (expanso-edge v2.1.21) against a local fixture, never on
Expanso Cloud:

| Run | Feed response | Job state | Records | Where it failed |
|---|---|---|---|---|
| Guarded | HTTP 200 | completed | 4 | did not fail |
| Guarded | HTTP 401 | failed | 0 | the guard: "feed fetch failed: ... 401 Unauthorized" |
| Guarded | HTTP 503 | failed | 0 | the guard: "feed fetch failed: ... 503" |
| Unguarded control | HTTP 401 | failed | 0 | the `xml` step |

This test did not reproduce a silent `completed` outcome for RSS: without
the guard the job still failed, one step later. The guard makes the cause
explicit and matches the lesson in `docs/llms.txt`. The separate finding
that an HTTP error can end as a `completed` job with nothing written came
from a different job, whose mapping turned the error body into zero
records.

## RAG URL-based chunk id (local-mode only, 2026-09-18)

The Cloud RAG runs built `chunk_id`, and so the Qdrant point id, from the
document's filename. Two documents with the same filename on different
paths therefore got the same point ids, and the second upsert overwrote the
first; the Cloud fixtures had unique filenames, so the runs above did not
show it. The published ingest spec builds `chunk_id` from the source URL
instead and keeps the filename as the display field `doc`.

Run on a local-mode node (expanso-edge v2.1.21, Qdrant 1.19.1, Ollama
0.33.2 with `nomic-embed-text`), never on Expanso Cloud, against fixture
documents `a/guide.md`, `b/guide.md` (same filename, different content)
and `c/unique.md`, 5 chunks in all:

| Run | Points stored | Result |
|---|---|---|
| Filename-based id (control) | 3 of 5 | `b/guide.md` overwrote `a/guide.md`'s chunks |
| URL-based id | 5 of 5 | distinct `source_uri` and `chunk_id` for every chunk |
| URL-based id, re-ingest | 5 | idempotent |

With the URL-based id, each test question's top hit came from the right
URL.

## restart_policy (added after the Cloud runs, 2026-09-18)

The field and its values `on-failure | always | never` come from Expanso
Cloud's own validation error on 2026-09-18; no documentation was found.
Both `expanso-edge validate` and `expanso-cli job validate --offline`
accept it.

- On Expanso Cloud, a failing bounded job with the default policy was
  rescheduled every few seconds while reading `running` (27 executions in
  54 s). With `never` the same job ended `failed` after 1 execution, and a
  successful job with `never` completed.
- On a local-mode node, a failing RAG ingest with `never` ended `failed`
  after 1 execution, and a successful RAG ingest with `never` completed
  with 5 points.

`restart_policy: never` was added to the six bounded job specs after the
Cloud runs of those jobs. They have not been re-run on Expanso Cloud with
it.
